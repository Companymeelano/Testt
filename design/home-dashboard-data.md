# Home dashboard: data and query inventory

## Scope and data boundary

The Home additions use the app's existing, read-only Atiran SQL connection and query builders. They add **no HTTP/API endpoint, SQL table, schema migration, or database write**. Schema-dependent fields are resolved by the existing `Meta`/query layer. If required data is unavailable, the affected card/alert is omitted or marked unavailable; values are not fabricated. The seeded cache in `HomeDashboardScreenshotTest` is instrumentation-only and is not a product/demo data source.

## Existing query inputs and returned fields

| Home capability | Existing query / source data | Fields consumed or returned |
|---|---|---|
| Daily sales, purchases, and trend | `Queries.factorDaily` over `sailfact` / `buyfact`; date, amount (`all`), and invoice number (`shfacfo` / `shfackh`) for filtering and de-duplication | `day`, `total`, `docs`. `Queries.salesOn` additionally returns `d`, `total`, `docs`, `parties`, `paid`, `discount`, `tax`. |
| Receipts/payments and cash breakdown | `MoneyQueries.darDay`, `darSummary`, `cashDaily`, and `paymentMix`; `dar` fields include `p`, date, booked total (`mab` when present), and available cash/cheque fields. POS, transfer, and cheque details use the existing Atiran detail tables where present. | Day: `d`, `total`, `cash`, `pos`, `havaleh`, `cheque`, `count`. Summary: `total`, `cash`, `pos`, `havaleh`, `cheque`, `count`, `breakdownAvailable`. Daily cash: `day`, `receipts`, `payments`, `net`, `docs`. Mix: `label`, `amount`, `docs`. A missing component is not treated as a confirmed zero. |
| Top customers / products | `Queries.factorByCustomer` reads invoice headers; `Queries.factorTopProducts` reads `sailfact`/`buyfact` and `subsailfact`/`subbuyfact`, with `inventory` names when available. Required line keys include invoice number, `SHKA`, quantity (`TEDVAH` aliases), and line amount (`LINESUM` aliases). | Customers: `label`, `total`, `docs`. Products: `label`, `qty`, `total`, `docs`. |
| Gross profit | `MasterQueries.profitDaily`: `sailfact` date, invoice number, and amount; `subsailfact` invoice link, `SHKA`, and quantity; `inventory` product key and recorded purchase-cost field (`inventory_price` / `buy_price` aliases). | `day`, `sales`, `cogs`, `profit`. This is the existing query's estimate using recorded item cost; the Home view does not write or alter accounting data. |
| Low/out-of-stock summary | `MasterQueries.productsSummary` reads `inventory` product key, stock (`mojkavah` aliases), and optional active, cost, and reorder-point fields. `stockAlerts` returns product details only when the schema supports them. | Summary: `count`, `active`, `activeKnown`, `low`, `out`, `value`, `reorderKnown`, `reorderN`. No unknown reorder point is interpreted as zero. |
| Returns | `MasterQueries.returnsByKindOn` reads dated, active `back_sanad` return documents and the existing return-kind relation. A date field is required for the day-close view. | `label`, `docs`, `total`. All-time totals are not substituted for a dated closeout. |
| Due cheques, overdue invoices, bounced cheques | `MoneyQueries.chequeDue` resolves the existing incoming/outgoing cheque source and maturity/status/amount fields; `Queries.overdueInvoices` reads `sailfact` settlement fields (`t_date`, `tasvieh`, `all_fel` / `all`); `MoneyQueries.bouncedTotal` reads the existing bounced-cheque flag. | Due cheque: `amount`, `sardate` (and existing list fields such as `num`, `statusLabel`, `customer`). Overdue invoice: `code`, `party`, `amount`, `dueDate`, `days`, `visitor`, `invoice`. Bounced total: `count`, `total`. |
| Purchase-price drift alert | Existing `Queries.buyPriceTrend` reads `buyfact` dates / invoice IDs and `subbuyfact` invoice link, `SHKA`, quantity, and `JOZPRICE`; `inventory` name is optional. `AlertEngine` compares the two latest available unit prices per product. | `label`, `lastUnit`, `prevUnit`, `change`, `docs`. An absolute change of 15% or more triggers the existing alert; invalid or missing prices are ignored. |
| Morning summary and unusual-sales notification | Existing `Queries.salesOn`, `MoneyQueries.darOn`, and `Queries.factorDaily` feed `SalesSnapshot` / `SalesComparison`; the current `AlertEngine` evaluates due items. | Summary requires both yesterday's `total` values (sales and receipts). Sales comparison uses up to four prior occurrences of the same weekday; the configured sales-drop threshold is local app settings. Missing query results suppress that message rather than substituting a value. |
| Seven-day forecast | Existing daily sales history from `Queries.factorDaily`; no new source. The `forecast_7d` Home section is **off by default** and requires at least two observed same-weekday samples for each forecast day. | Seven calendar days; expected value is the four-week same-weekday mean and the band is mean ± sample standard deviation (not a confidence interval). Friday is treated as an observed weekday; official holidays are not inferred. |

## Local-only inputs

Home section order/visibility, monthly sales target, closeout opening/counted cash, market-rate comparison history, notification enablement, quiet-hours interval, and alert thresholds are stored by the existing app settings/preferences layer on the device. They are not written to the Atiran database. Navigation shortcuts and the seasonal-calendar display require no data endpoint. The cash-flow view is not described as a bank-balance reconciliation.

## Required API/endpoint fields

**None for this implementation.** There is no new remote API. If an API-backed implementation is proposed later, it must be separately specified against these query outputs; no endpoint or schema field should be inferred from the UI.
